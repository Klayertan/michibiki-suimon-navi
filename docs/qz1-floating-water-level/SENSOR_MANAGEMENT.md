# 水位センサー管理 / Water-Level Sensor Management

QZ1/QZ1LE を「水位センサー」としてスイスイナビに登録し、圃場と対応づけ、設定し、
データを見るための機能。

> **重要 / 実装状況について。** このドキュメントは「実装済み」と「未実装」を
> 明示的に区別します。GNSSの標高から水位を測れるという仮説は**まだ実験的に
> 検証されていません**。センサー管理・圃場割り当ては動作しますが、
> **絶対水深の表示は、鉛直変位実験による裏付けがない限り拒否されます。**
> 詳細は [EXPERIMENT.md](EXPERIMENT.md)。

---

## 1. モデル / The model

```text
物理デバイス
QZ1-FLOAT-001            ← 固定ID。機器そのもの
       │
       │ 人が確定した割り当て
       ▼
登録済み圃場
paddy-001 / 田圃1
       │
       ▼
センサー設定
  ├── データ取得（接続方法・オンライン判定）
  ├── 較正（水位基準）
  ├── 品質判定（fix/衛星数/HDOP/フィルタ）
  └── 表示設定
       │
       ▼
測定 → データ表示 → 既存の水管理判断へ
```

**`sensorId` と `fieldId` は別物です。** 同じ個体を別の圃場へ移しても
`sensorId` は変わりません。これは [SENSOR_FIELD_ASSIGNMENT.md](SENSOR_FIELD_ASSIGNMENT.md)
から続く不変条件です。

---

## 2. 画面 / Where it lives

`設定` → `圃場データ` ワークスペース → **水位センサー** カード。

1枚のカードの中に、排他的な4つの画面があります。

| 画面 | 目的 |
|---|---|
| 一覧 | どのセンサーが、どの圃場に、つながっているか、現在値、健全か |
| 追加 | 5ステップのウィザード |
| 設定 | そのセンサーの構成 |
| データ | 実測値・GNSS・圃場検出・水管理判定 |

**恒久的に全部を表示しません。** 地図が使えなくなるためです（§43 の禁止事項）。
通常の一覧が答えるのは4つの問いだけで、詳細は1クリック先にあります。

圃場側からも見えます: `圃場の管理` カード → 現在の圃場 → **水位センサー**。
未設定なら「センサーを割り当て」ボタンが出ます。

---

## 3. 割り当ての正準な向き / One canonical relationship

**`sensor.assignedFieldId` が唯一の真実です。**

`field.sensorId` は **存在しません**。圃場側の表示は毎回レジストリから
逆引きして計算します。2箇所に保存すればいずれ食い違いますが、
1箇所＋導出なら食い違えません。

```javascript
// 正準
sensor.assignedFieldId === "paddy-001"

// 逆引き（導出・保存しない）
registry.listForField("paddy-001")      // → [sensor, ...]
registry.primaryWaterSensor("paddy-001") // → sensor | null
```

1圃場に複数センサーを持てる余地はデータモデルに残してあります
（`listForField` は配列を返します）。`primaryWaterSensor()` は先頭を返すだけで、
競合する `primary` フラグは導入していません。

---

## 4. 自動検出は「提案」です / Detection suggests, never assigns

GNSS位置から候補圃場を提示します。**自動では割り当てません。**

```text
現在位置から推定

田圃1 / paddy-001
検出一貫性 90%

[この圃場を使う]
```

* `detectedFieldId` — 観測。毎秒変わる
* `assignedFieldId` — 人の判断。ボタンを押したときだけ変わる

`assignedFieldId` を書き換えるコードは `FloatingSensorRegistry.assign()` の
**1箇所だけ**で、検出結果からそこへ至る経路はありません。

### 検出一貫性は確率ではありません

`検出一貫性 90%` は **直近10サンプルのうち9件が一致した**という意味です。
「90%の確率でこの圃場が正しい」という意味では**ありません**。

**系統的なGNSSバイアスや、歩いて測った圃場境界そのものの誤差があると、
一貫性100%のまま地理的に間違っていることがあります。** 畦から1〜2mの位置に
浮体を置いた場合は特にそうです。詳細は
[SENSOR_FIELD_ASSIGNMENT.md §4](SENSOR_FIELD_ASSIGNMENT.md)。

サンプルが0件のときは `0%` ではなく `—` を表示します。0%は「照合して一致
しなかった」と読めてしまい、実際は「まだ照合していない」ためです。

---

## 5. 再割り当て / Reassignment

明示的な確認を求めます。

```text
このセンサーの割当圃場を変更しますか？

現在:
田圃1 / paddy-001

変更後:
田圃5 / paddy-005

過去の測定記録の圃場IDは変更されません。
```

履歴は追記のみで、`removed` → `assigned` の2件として記録します。

**過去の測定は取得時点の圃場IDを保持します。** 遡って書き換えません。

---

## 6. 移動の警告 / Movement warning

割り当て済みのセンサーが継続的に別の圃場で検出されると警告を出します。
**割り当ては自動変更しません。**

しきい値は「連続3回の確信ある不一致」。ウィンドウが新しい圃場で確信を持つのに
10サンプル、そこから3回で合計およそ13サンプル（1Hzで約13秒）です。

---

## 7. 較正 / Calibration — ここが最重要

画面は3つの量を**常に別行**で出します。

```text
① GNSS標高        42.347 m
② 相対高度変化    +32 mm      ← 水深ではありません
③ 較正水深        表示できません
```

較正の入力は「実測水深」と「現在のGNSS標高」の2つで、式は既存の
`calibration.js` のものをそのまま使います（UIで別の式を作っていません）。

```text
H(t) = H0 + (Z(t) − Z0)
```

### 較正しても水深が出ないことがあります（正常な動作です）

`calibration.js` は次の場合に水深の算出を**拒否**します。

| 状態 | 表示 |
|---|---|
| 較正なし | `未較正` |
| 較正あり・検証実験なし | `表示できません` ＋ 理由 |
| 較正あり・検証実験が何も測定できなかった | `表示できません` ＋ 理由 |
| 要求分解能 > 実証済み分解能 | `表示できません` ＋ 理由 |
| 較正が古い | `表示できません` ＋ 理由 |

**現状、鉛直変位実験は未実施です。** したがって実測入力で較正しても
`較正が無効`（検証実験が紐づいていない）となり、絶対水深は表示されません。
これは不具合ではなく、この機能の中心的な安全装置です。

実験を実施して合格した段差があれば、その解析結果が較正に添付され、
実証済み分解能の範囲内でのみ水深が表示されるようになります。

---

## 8. 水管理判断との関係 / Sensor evidence vs agronomic decision

```text
測定 → 品質判定 → 較正 → 水深
                              │
                              ▼
                  既存の水管理エンジン（js/water/）
```

センサー層は**証拠を供給するだけ**です。目標水位・しきい値・推奨は
既存の水管理ドメインが決めます。センサーコントローラ内に農学的しきい値を
作っていません。

較正済み水深がない場合、判定欄は判定を出さず、その理由を表示します
（相対高度変化を絶対水深を期待するモデルに流し込みません）。

## 9. 設定項目 / Settings

| グループ | 項目 |
|---|---|
| 基本設定 | 表示名、機種、割当圃場（センサーIDは固定・変更不可） |
| データ取得 | 接続方法、オンライン判定時間、接続状態、最終受信 |
| 水位基準 | 較正状態、較正日時、実測水深入力、較正解除 |
| 品質判定 | フィルタ、最小衛星数、HDOP上限、絶対水深の表示可否 |

**表示名とセンサーIDは別物です。** 表示名を変えても `sensorId` は変わらず、
測定記録・割り当て・履歴はすべて `sensorId` に紐づいたままです。

不正な入力は**部分適用せず全体を拒否**し、理由を全部表示します。
一方、保存済みデータが壊れていた場合は項目ごとに既定値へ**修復**します
（農家が対処できないため）。

## 10. 永続化 / Persistence

キー: `suimonNaviFloatingSensorsV1`（`js/cloud/user-scope.js` でアカウント
スコープ済み）。

**キー名はV1のまま、スキーマ版だけを2に上げています。** レコードは
「増えた」だけで、名前変更も削除もありません。

| V1 | V2 での扱い |
|---|---|
| `sensorId` | そのまま |
| `label` | 保持。`displayName` が空ならこれを表示に使う |
| `assignedFieldId` | そのまま |
| `assignmentHistory` | そのまま |
| `lastPosition` / `lastSeenAt` | そのまま |
| — | `displayName` 追加（V1の `label` を引き継ぐ） |
| — | `deviceModel` 追加（既定 QZ1） |
| — | `settings` 追加（既定値） |
| — | `calibration` 追加（null） |

**壊れた較正レコードは修復しません。** そのまま通して `calibration.js` に
毎回判定させます。ここで修復することは「水深を表示してよい」という許可を
捏造することになるためです。

## 11. 実装 / Implementation

| ファイル | 役割 | DOM |
|---|---|---|
| `platform-capabilities.js` | ブラウザ機能検出（UA判定なし） | なし |
| `sensor-transport.js` | 取得経路の抽象化・測定値の正規化 | なし |
| `sensor-settings.js` | 設定スキーマ・検証・品質判定・較正状態 | なし |
| `sensor-view-model.js` | 画面に出す値の決定（水深を出してよいか等） | なし |
| `sensor-registry.js` | センサー同一性・割り当て・履歴・永続化 | なし |
| `sensor-management-controller.js` | カードのDOM・ボタン・画面切替 | あり |

判断はすべてDOMなし側にあり、単体テストで固定されています。

**セキュリティ:** センサー表示名・圃場名・取り込んだメタデータは
すべて信頼できない文字列として扱い、`textContent` 経由でのみDOMに入れます。
データを差し込む `innerHTML` はこのカードに存在しません。

| 機能 | 状態 |
|---|---|

| 圃場の割り当て・逆引き・再割り当て・履歴 | **実装済み** |
| GNSSによる圃場提案・移動警告 | **実装済み** |
| 設定の保存・読込・V1移行 | **実装済み** |
| 較正の保存・水深表示の門番 | **実装済み** |
| USB/シリアル接続 | **実装済み**（既存パイプラインを利用） |
| NMEAファイル読込 | **実装済み**（既存アップローダを利用） |
| Bluetooth (GATT) 直接接続 | **未実装** — モデルにはあるが接続コードなし |
| クラウド/ゲートウェイ受信 | **未実装** — モデルにはあるが受信エンドポイントなし |
| 測定履歴の永続化・時系列グラフ | **未実装** |
| 登録済み圃場カードへのセンサー表示 | **未実装**（現在は圃場の管理カード側に表示） |
| センサーのプロジェクトJSON書き出し | **未実装** |

未実装の経路はUIで「このアプリで未実装です」と表示され、選択できません。
**押せない・押しても何も起きないボタンは出しません。**
