# Sensor Identity and Automatic Field Detection

浮体センサが「自分がどの圃場にいるか」を知る必要をなくすための仕組み。

**この機能は標高実験とは独立しています。** GNSSの標高が水位計測に使えるかどうかの
結論がどうであれ、緯度・経度による圃場の自動判定はそのまま機能します。

---

## 1. センサIDと圃場IDは別のもの / Sensor identity ≠ field identity

センサが知っていること:

```text
QZ1-FLOAT-001
```

スイスイナビが判定すること:

```text
paddy-003（北の田）
```

判定の材料はGNSS位置と、農家が既に登録した圃場ポリゴンだけです。

```text
QZ1 / QZ1LE
      |
      | GNSS / NMEA（既存のシリアル経路）
      v
既存のGNSSパイプライン（js/gnss/nmea-parser.js）
      |
      v
   1つの測位点
      |
      +------> 標高 -----> 鉛直変位の実験（experiment-controller.js）
      |
      +------> 緯度・経度 -> 圃場判定（field-detection.js）
                                 |
                                 v
                          登録済み圃場ポリゴン
                                 |
                                 v
                          センサの割り当て（sensor-registry.js）
```

### この分離の利点 / Why this is worth the separation

| | |
|---|---|
| **圃場ごとのファームウェアが不要** | 出荷時の設定は自分のIDだけ。どの田んぼに入れても同じ個体です |
| **田んぼ間で移動できる** | 拾って別の圃場に入れ直すだけ。書き換えるものはありません |
| **割り当てが一箇所に集まる** | 「どのセンサがどの圃場か」はこのアプリだけが持ちます。現場の機器に散らばりません |
| **移動を自動検知できる** | 割り当てと検出結果を突き合わせられます（§5） |
| **過去の測定が追跡可能** | 各測定は取得時点の圃場IDを持ち続けます（§6） |
| **通信方式に依存しない** | USB / BLE / Wi-Fi / LoRa のどれになっても、この層は変わりません |

## 2. 検出圃場 と 割り当て圃場 / Detected vs assigned

**この2つは絶対に混ぜません。**

| | 何であるか | いつ変わるか |
|---|---|---|
| `detectedFieldId` | GNSS位置からの**観測** | 毎秒、勝手に |
| `assignedFieldId` | 人が下した**判断** | 人がボタンを押したときだけ |

一致している状態:

```text
sensorId:       QZ1-FLOAT-001
detectedField:  paddy-003
assignedField:  paddy-003
```

食い違った状態:

```text
detectedField:  paddy-007
assignedField:  paddy-003
```

このとき**自動では割り当て直しません**。センサが本当に移動したのか、畦際で位置が
揺れているのか、圃場の境界の測り方がずれていたのか、ここからは区別できないからです。
警告を出して、判断は人に返します。

`assignedFieldId` を書き換えるコードは `FloatingSensorRegistry.assign()` の1箇所だけで、
検出結果からそこを呼ぶ経路はありません。

## 3. 点の内外判定 / Point-in-polygon

`js/qz1-water-level/field-detection.js`

* **Turfが読み込まれていればTurfを使います**（`turf.booleanPointInPolygon`）。
  未読込・例外時は同じ判定をするレイキャスティングにフォールバックします。
  既存の `polygonAreaSquareMeters()` が `turf.area` に対して取っている構えと同じです。
* **座標順**: このアプリの境界は `[緯度, 経度]`（Leaflet順）。GeoJSON/Turfは
  `[経度, 緯度]`。変換は `toGeoJsonRing()` の1箇所だけで行い、リングも閉じます。
  取り違えると北緯34度・東経135度の田んぼが地中海に飛び、全部「圃場の外」になります。
* **圃場データは既存のものだけ**を読みます。2つ目の圃場データベースは作っていません。
  Stage-1形式（`coordinates` 直下）と測量チェック形式（`boundary.coordinates`）の
  両方を読みます。

判定結果は5つ:

| status | 意味 |
|---|---|
| `inside` | ちょうど1つの圃場に含まれる |
| `outside` | 有効な位置を有効なポリゴンと照合し、どれにも含まれない |
| `ambiguous` | 2つ以上に含まれる（**勝手に1つ選びません**、§7） |
| `invalid-position` | 位置そのものが使えない（欠測・NaN・範囲外） |
| `no-fields` | 照合できるポリゴンが1つもない（`outside` とは別物） |

**壊れたポリゴンは飛ばして、IDを報告します。** 黙って捨てると、判定できなかった
ことが自信のある「圃場の外」に化けます。

> **注意:** `field-annotation-core.js` の `isPointInsideBoundary()` は再利用して
> いません。あちらは3点未満の境界に対して `true` を返す仕様（「明らかに外なら
> 警告する」ための緩い判定）で、そのままではセンサが2点しかない境界トラックの
> 「中にいる」と報告されてしまいます。レイキャスティングの計算式は同じで、
> 退化した図形の扱いだけが違います。

## 4. GNSSの揺れへの対処 / Jitter and detection consistency

`js/qz1-water-level/detection-window.js`

浮体は動きませんが、**報告される位置は動きます。** 畦の幅はメートル単位ではなく、
このリポジトリの実測ログ（`data/samples/qz1-dorm-walk-20260706.txt`）では静止した
受信機の位置が数メートル揺れています。

なので **1サンプルでは判定しません。** 直近の有効サンプルの多数決を取り、
一致した割合を**検出一貫性**として出します。これは直近ストリームの一致率であり、
地理的に正しい確率ではありません。

```text
直近10サンプル:

paddy-003
paddy-003
paddy-003
paddy-003
paddy-003
paddy-003
paddy-003
paddy-003
OUTSIDE
paddy-003
```

```text
candidate:  paddy-003
detection consistency: 0.9
```

| 既定値 | 値 | 意味 |
|---|---|---|
| `windowSize` | 10 | 記憶する有効サンプル数 |
| `candidateThreshold` | 0.8 | 候補と認めるのに必要な一致率 |
| `minSamples` | = windowSize | 判定を出す前に必要な最小サンプル数 |

**これらは工学的な初期値であって、実験で裏付けた定数ではありません。** すべて
コンストラクタ引数です。

いくつかの設計上の判断:

* **無効な位置は投票しません**（数えはします）。測位を失った瞬間の受信機に、
  浮体が真ん中に浮いている圃場へ反対票を投じさせないためです。
* **「圃場未登録」は「圃場の外」として投票しません。** 別の事実です。
* **`outside` と `ambiguous` も勝てる選択肢です。** 本当に登録圃場の外にある浮体は、
  永久に「検出中」ではなく、はっきり「外」と言えなければなりません。
* **`minSamples` の既定はウィンドウ全体です。** 到着済みサンプル数で割ると最初の
  1件が満場一致になり、電源投入1秒後に自信満々の候補を出してしまいます。

### 境界付近の限界 / The boundary limitation

**検出一貫性は「直近の測位が一致した」という意味であって、「正しい」という意味では
ありません。**

1 Hzで10サンプルは10秒です。GNSS誤差の相関はそれよりずっと長く続くので、
**境界の外側1〜2 mに浮体があると、10回連続で同じ間違った答えを出して検出一貫性1.0に
達することがあります。** ウィンドウが守ってくれるのは短時間のちらつきだけで、
系統的な偏りには無力です。

畦際に設置した浮体では:

* 割り当ての確定前に、時間を置いて何度か確認してください
* 圃場境界そのものの測量精度も効いてきます（歩いた軌跡の誤差がそのまま乗ります）
* 迷ったら、浮体を圃場の中心寄りに設置してください

## 5. 割り当ての状態遷移 / Assignment state machine

`js/qz1-water-level/sensor-registry.js`

```text
unassigned
    ↓  測位が届き始める
detecting
    ↓  ウィンドウが閾値を超える
candidate paddy-003
    ↓  ★ 人が「割り当てる」を押す ★
locked paddy-003
```

全状態:

| 状態 | 意味 |
|---|---|
| `unassigned` | 未割り当て・証拠なし |
| `detecting` | 未割り当て・ウィンドウ充填中 |
| `candidate` | 未割り当て・1つの圃場が閾値を超えた |
| `locked` | 割り当て済み・確定 |
| `outside-known-fields` | 未割り当て・登録圃場のどれにも入っていない |
| `ambiguous` | 未割り当て・複数の圃場に入っている |
| `moved-warning` | 割り当て済みだが、継続的に別の圃場で検出されている |

**割り当て済みのセンサは `locked` か `moved-warning` にしかなりません。**
検出ウィンドウがどう転んでも `candidate` や `ambiguous` に引き戻されることは
ありません。それらは「圃場を選ぶ」ための状態で、このセンサはもう選び終えて
います。「1つのノイズで locked が変わってはいけない」は、1000個のノイズでも
同じです（テストで固定しています）。

### 移動の警告 / Movement warning

```text
⚠ センサが移動した可能性があります

割り当て: paddy-003（北の田）
検出:     paddy-007（南の田）
```

* **連続して**、**確信のある**、**同じ別圃場を指す**ウィンドウ判定を数えます
* 割り当て先と一致した判定、または確信のない判定が1回でも入るとカウントは0に戻ります
* 2つの隣接圃場を交互に指す場合はカウントが伸びません（それは境界であって移動ではありません）
* 既定のしきい値は連続3回。ウィンドウが新しい圃場で確信を持つのに10サンプル、
  そこから3回で、**合計およそ13サンプル**（1 Hzで約13秒）です
* **`assignedFieldId` は変更しません。** 表示上の状態が変わるだけです

## 6. 過去の測定 / Historical measurements

測定レコードは、**取得時点で割り当てられていた圃場ID**を焼き込みます。

```json
{
  "timestamp": "2026-08-29T01:00:00.000Z",
  "sensorId": "QZ1-FLOAT-001",
  "fieldId": "paddy-003",
  "assignmentStatusAtMeasurement": "locked",
  "relativeHeightMm": 32
}
```

後で浮体を paddy-005 に移しても、**この記録は paddy-003 のままです。**
そこで測った水は実際に paddy-003 にあったからです。遡って書き換えると、
1シーズン分の記録が黙って付け替わります。

未割り当てのセンサは `fieldId: null` を書きます。検出結果で埋めることはしません
（検出は割り当てではありません）。

### 割り当て履歴 / Assignment history

各センサは追記のみの履歴を持ちます。

```text
2026-08-29  assigned  paddy-003
2026-09-10  removed   paddy-003
2026-09-12  assigned  paddy-005
```

既存の割り当てに上書きした場合も、`removed` → `assigned` の2件として記録します。
1件だけだと「最初からそこにいた」ように読めてしまうためです。

## 7. 例外的な状況 / Edge cases

### 登録圃場の外

```text
検出圃場
登録圃場の外
```

`detectedFieldId = null`。**最も近い圃場を勝手に選びません。** 内外判定と
近傍探索は別の操作で、聞かれたのは前者です。

### 複数の圃場が重なっている

```text
検出圃場
重複（判定不能）

paddy-003（北の田） / paddy-009（重なる田）
```

`assignmentStatus = ambiguous`。候補IDはUIとデバッグ表示に出します。
**配列の先頭を黙って選びません** — それは農家が登録した順序であって、
センサがどこにあるかの事実ではありません。

### 圃場を編集した

登録・編集・削除で圃場の集合が変わると、ウィンドウの投票を破棄します。
古い票は違う地図に対して投じられたもので、もう証拠ではありません。

## 8. 実装 / Implementation

| ファイル | 役割 | DOM |
|---|---|---|
| `js/qz1-water-level/field-boundary.js` | 2種類の圃場レコード形状から境界を読む | なし |
| `js/qz1-water-level/field-detection.js` | 内外判定（Turf優先・フォールバックあり） | なし |
| `js/qz1-water-level/detection-window.js` | 揺れ対策のローリングウィンドウと検出一貫性 | なし |
| `js/qz1-water-level/sensor-registry.js` | センサの同一性・状態遷移・移動監視・履歴・永続化 | なし |
| `js/qz1-water-level/sensor-field-controller.js` | カードのDOM・地図マーカー・ボタン | あり |

永続化キー: `suimonNaviFloatingSensorsV1`（`js/cloud/user-scope.js` でアカウント
スコープ化済み）。**圃場IDは持ちますが、圃場のジオメトリは持ちません。**
境界の置き場所は `suimonNaviFieldAnnotationsV2` のままです。

地図マーカーは**共有の地図**に自前のレイヤグループを足す形です
（`vegetation-controller.js` / `paddy-intelligence.js` と同じ作法）。
2つ目の地図は作っていません。

### 通信方式からの独立 / Transport independence

このミルストーンでは新しい無線は実装していません。既存のQZ1シリアル/NMEA経路を
そのまま使います。圃場割り当てのロジックは `{ lat, lon, altitude }` を持つ
測位点しか見ないので、後で USB / BLE / Wi-Fi / LoRa のどれになっても
このドメインロジックは変わりません。

## 9. 次のミルストーン / Deliberately deferred

* **登録済み圃場カードへのセンサ表示。** いまは水位実験カード側に
  「この圃場に割り当て済みのセンサ」を出しています。`field-annotation-controller.js`
  の `renderRegisteredList()` に差し込むには、あのコントローラにセンサレジストリを
  注入する必要があり、この機能とは無関係な範囲に手が入ります。
* **センサのプロジェクトJSONへの書き出し/取り込み。** 現状のエクスポートは
  圃場ストアだけを見ています。センサを含めるにはエクスポート形式とクラウド同期
  （`js/cloud/field-sync-core.js`）の両方を触ることになります。
* **測定レコードの永続化。** `buildSensorMeasurement()` は正しい圃場IDを刻んだ
  レコードを返しますが、それを保存する先はまだありません。水位の測定値が
  実験段階を出てからで十分です。
* **複数センサの同時運用。** レジストリは複数持てますが、カードは一度に1台を
  表示します。
