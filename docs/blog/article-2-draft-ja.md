## はじめに

**本記事は、さくらのクラウド検定 学生アンバサダーとして執筆しています。**

こんにちは。学生エンジニアです。

1本目では、水田の水管理支援Webアプリ「スイスイナビ」のPython（API）を、さくらのクラウドのサーバーに載せました。今回は、そのAPIを使う側、つまり**スイスイナビの画面（アプリ本体）を、さくらのレンタルサーバで見られるようにする**話です。

きっかけは、自分のアプリのアドレス `https://suisuinavi.sakura.ne.jp/` を開いたら、**アプリではなく、このブログのトップページに飛ばされた**ことでした。

この記事のゴールは、次のとおりです。

> `https://suisuinavi.sakura.ne.jp/` を開くとスイスイナビが表示される。ブログ（`https://sakurakai.sakuraweb.com/`）は、これまでどおり表示される。

想定している読者は「レンタルサーバにHTMLを置いたことはあるけれど、`.htaccess` はよく分からない人」です。専門用語は、その都度短く説明します。**うまくいかなかったことも書きます。**

## 用語を先に

| 言葉 | ひとことで |
|---|---|
| 公開フォルダー（ドキュメントルート） | ドメインにアクセスしたとき、サーバーのどのフォルダーの中身を見せるか、という「入口のフォルダー」。レンタルサーバのコントロールパネルでは「WEB公開フォルダー」と表示される |
| ホスト名 | ブラウザが「このアドレスを開きたい」とサーバーに伝える名前。`suisuinavi.sakura.ne.jp` や `sakurakai.sakuraweb.com` のこと。同じサーバーでも、ホスト名で処理を変えられる |
| `.htaccess` | フォルダーに置く、Apache（ウェブサーバー）への設定ファイル。転送や、アクセスの振り分けを書ける |
| 301（リダイレクト） | 「このアドレスは引っ越しました。新しいアドレスはこちら」というお知らせ。ブラウザは、これを**覚えておく**ことがある |
| 書き換え（リライト） | 届いたアドレスを、サーバーの内側でこっそり別の場所に読み替えること。転送と違い、ブラウザのアドレス欄は変わらない |
| 404 / 403 / 500 | 「見つからない」「見せられない」「サーバー側の失敗」を表す番号 |

## 状況を調べる

### まず症状を確かめる

`curl` というコマンドで、アドレスを開いたときのサーバーの返事（ヘッダー）だけを見ます。

```
curl -sI https://suisuinavi.sakura.ne.jp/ | grep -i -E "^(HTTP|location)"
```

- `curl -sI`：`-s` は余計な表示を出さない、`-I` は本文ではなく返事の先頭部分（ヘッダー）だけを取る
- `grep -i -E "^(HTTP|location)"`：その中から「HTTP」で始まる行と「location」の行だけを残す

結果は次のとおりでした。

```
HTTP/2 301
location: https://sakurakai.sakuraweb.com/
```

つまり、サーバーが「このアドレスは `sakurakai.sakuraweb.com` に引っ越しました」と答えていました。`/index.html` や `/js/app.js` など、**どのアドレスでも同じ**でした。アプリを見られるのは、副系として置いてあるGitHub Pagesだけの状態です。

### コントロールパネルで設定を見る

さくらのレンタルサーバのコントロールパネルを、**見るだけ**のつもりで開きました。まず「ドメイン/SSL」の一覧です。

![ドメイン/SSLの一覧。2つのドメインが、どちらも公開フォルダー ~/www/ を指している](media:a2-01-domain-list-both-www.jpg)

ここで分かったのは、**2つのドメイン（アプリ用の `suisuinavi.sakura.ne.jp` と、ブログ用の `sakurakai.sakuraweb.com`）が、同じ公開フォルダー `~/www/` を指している**ことです。図にすると、こうです。

| ブラウザで開くアドレス | 見せるフォルダー |
|---|---|
| `suisuinavi.sakura.ne.jp` | `~/www/` |
| `sakurakai.sakuraweb.com` | `~/www/`（同じ場所） |

### ファイルマネージャーで中身を見る

次に、ファイルマネージャー（ブラウザでサーバーのファイルを見られる画面）で `~/www/` の中身を見ました。

![~/www/ の中身。ブログ用の index.php と .htaccess、michibiki フォルダーだけで、アプリのファイルは見当たらない](media:a2-02-www-folder-before.jpg)

あったのは、ブログ（WordPress）用の `index.php` と `.htaccess`、それに `michibiki` フォルダー（WordPress本体）だけです。**スイスイナビのファイル（`index.html`、`css/`、`js/` など）は、どこにもありませんでした。**

GitHubの自動デプロイの記録を見ると、最後に成功したのは9月6日でした。その後、9月11日にブログの置き場所を整理した設定が入っています。ただ、アプリのファイルが**いつ、なぜなくなったかは、記録が残っておらず分かりません**。

### `.htaccess` の中身

最後に `.htaccess` を開きました。

![.htaccess のプレビュー。いちばん上に、suisuinavi.sakura.ne.jp からブログへ転送する決まりがあった](media:a2-03-htaccess-old-redirect.jpg)

いちばん上に、9月12日の日付つきで、こんな決まりが入っていました。

```
# BEGIN old-host redirect 2026-09-12 (permanent 301, host-based only)
<IfModule mod_rewrite.c>
RewriteEngine On
RewriteCond %{HTTP_HOST} ^(www\.)?suisuinavi\.sakura\.ne\.jp$ [NC]
RewriteRule ^(.*)$ https://sakurakai.sakuraweb.com%{REQUEST_URI} [R=301,L]
</IfModule>
# END old-host redirect 2026-09-12
```

読み方は次のとおりです。

- `RewriteCond %{HTTP_HOST} ^(www\.)?suisuinavi\.sakura\.ne\.jp$`：条件。「ホスト名が `suisuinavi.sakura.ne.jp`（先頭に `www.` が付いてもよい）のとき」
- `[NC]`：大文字小文字を区別しない
- `RewriteRule ^(.*)$ https://sakurakai.sakuraweb.com%{REQUEST_URI} [R=301,L]`：「どんなアドレスでも、同じ道筋のまま `sakurakai.sakuraweb.com` へ301で転送する。ここで終わり（`L`）」

日付とコメントから考えると、ブログの置き場所を `sakurakai.sakuraweb.com` に移したとき、**古いアドレスのブログ記事が見つからなくならないように**入れた決まりだと思います。ところがこれは「ブログだけ」ではなく、`suisuinavi.sakura.ne.jp` への**すべてのアクセス**を転送してしまいます。アプリのアドレスまで、ブログに飛ばされていた原因はこれでした。

## 直し方を決める

「転送の決まりを消せば解決」とはいきません。理由は2つあります。

1. 消すと、古いアドレスのブログ記事（`suisuinavi.sakura.ne.jp/michibiki/…`）が見つからなくなる。
2. 2つのドメインが同じ公開フォルダーを見ているので、アプリのファイルを `~/www/` の直下に置くと、ブログのファイルと混ざる。

そこで、次の方針にしました。

- `~/www/` の中に、アプリ専用のフォルダー `suisuinavi/` を作ってアプリを置く。
- `.htaccess` で、**ホスト名が `suisuinavi.sakura.ne.jp` のときだけ**、内側で `suisuinavi/` に読み替える。
- `suisuinavi.sakura.ne.jp/michibiki/…`（古いブログのアドレス）だけは、今までどおりブログへ301で転送する。
- `sakurakai.sakuraweb.com`（ブログ）には、触らない。

## 手順

### 1. 変更の前に、控えを作る

`.htaccess` はブログも支えているので、壊すとブログも見られなくなります。まず控えを作りました。ファイルマネージャーで `.htaccess` を選び、「整理」→「指定の名前で複製」で `.htaccess.bak-20261011` という名前にします。

![変更の前に、.htaccess の控え（.htaccess.bak-20261011）を作った。サイズは同じ746B](media:a2-04-htaccess-backup.jpg)

元に戻したくなったら、この控えを `.htaccess` に上書きコピーすれば、今日の作業を始める前の状態に戻ります。

### 2. アプリ用のフォルダーを作る

「表示アドレスへの操作」→「フォルダ作成」で、`~/www/` の中に `suisuinavi` を作りました。

![アプリ用のフォルダー suisuinavi を作った](media:a2-05-app-folder-created.jpg)

### 3. アプリのファイルを置く

アプリは、HTMLとJavaScriptだけの静的なファイルです。自動デプロイが送っていたのと同じもの（`index.html`、`css/`、`js/`、`config/`、`data/`）を、GitHubの `main` ブランチから取り出して、zipにまとめました。

```
git archive --format=zip origin/main index.html css js config data -o suisuinavi-app.zip
```

- `git archive`：リポジトリの中身を、`.git` などの余計なものを含めずに固めるコマンド
- `origin/main`：GitHub上の `main` ブランチ（自動デプロイが送っていたのと同じ版）
- 後ろの5つ：入れるファイルとフォルダー。**アプリに必要な公開ファイルだけ**で、パスワードなどの秘密は入っていません

このzip（約486KB）を、ファイルマネージャーの「アップロード」で `suisuinavi/` に入れ、「整理」→「リモートで解凍」で、**サーバーの上で**解凍しました。

![zipを解凍すると、index.html、css、js、config、data が並んだ](media:a2-06-app-files-unpacked.jpg)

この時点では、まだ `.htaccess` を変えていないので、アプリは `sakurakai.sakuraweb.com/suisuinavi/` のほうでは開けますが、`suisuinavi.sakura.ne.jp` はまだブログに飛びます。

### 4. `.htaccess` の最初の決まりを書き換える

`.htaccess` の最初のブロック（9月12日の転送）を、次の内容に置き換えました。

![.htaccess の先頭を書き換えた（保存前）](media:a2-07-htaccess-first-version.jpg)

```
# BEGIN suisuinavi host mapping 2026-10-11
<IfModule mod_rewrite.c>
RewriteEngine On
RewriteCond %{HTTP_HOST} ^(www\.)?suisuinavi\.sakura\.ne\.jp$ [NC]
RewriteRule ^michibiki(/.*)?$ https://sakurakai.sakuraweb.com/michibiki$1 [R=301,L]
RewriteCond %{HTTP_HOST} ^(www\.)?suisuinavi\.sakura\.ne\.jp$ [NC]
RewriteCond %{REQUEST_URI} !^/suisuinavi/
RewriteRule ^(.*)$ /suisuinavi/$1 [L]
</IfModule>
# END suisuinavi host mapping 2026-10-11
```

2つの決まりが入っています。

- **1つ目**：ホスト名が `suisuinavi.sakura.ne.jp` で、アドレスが `michibiki` で始まるとき、同じ道筋のまま `sakurakai.sakuraweb.com/michibiki…` へ301で転送する。古いブログのアドレスは、今までどおり引っ越し先に案内される。
- **2つ目**：ホスト名が `suisuinavi.sakura.ne.jp` なら、アドレスの頭に `/suisuinavi/` を付けて読み替える（転送ではなく**内側の書き換え**なので、アドレス欄は変わらない）。`RewriteCond %{REQUEST_URI} !^/suisuinavi/` は、「すでに `/suisuinavi/` で始まっているときは、もう書き換えない」という条件で、**同じ書き換えをいつまでも繰り返す**のを防ぎます。

ブログ側（`sakurakai.sakuraweb.com`）は、ホスト名の条件に合わないので、この決まりは素通りします。

### 5. 確かめる

ブラウザで確かめる前に、まず `curl` で確かめました。ブラウザは、前の301を覚えていて、古い転送のまま動くことがあるからです。

```
curl -s -o /dev/null -w "%{http_code}\n" https://suisuinavi.sakura.ne.jp/
```

- `-o /dev/null`：本文は捨てる
- `-w "%{http_code}\n"`：代わりに、返事の番号だけを表示する

`200` が返りました。続けてブラウザで開くと、スイスイナビの画面が表示されました。

![https://suisuinavi.sakura.ne.jp/ で、スイスイナビの画面が表示された](media:a2-09-app-live.jpg)

## つまずいたこと

**① 存在しないアドレスが「500」になった**

画面が開いたので安心しましたが、念のため、**存在しないアドレス**も `curl` で確かめました。

```
/robots.txt     → 500
/favicon.ico    → 500
/no-such-page   → 500
```

本来は「見つからない（404）」のはずです。「500」はサーバー側の失敗を表す番号で、検索エンジンのロボットが最初に見に来る `robots.txt` が500だと、「このサイトは壊れている」と受け取られかねません。

原因は、書き換えが**繰り返しになっている**ことだと考えています。

1. `/robots.txt` が届く → 私の決まりで `/suisuinavi/robots.txt` に読み替えられる
2. そのファイルは無い → ブログ（WordPress）の標準の決まり「ファイルでもフォルダーでもなければ `/index.php` に任せる」が働く
3. `/index.php` が届く → また私の決まりで `/suisuinavi/index.php` に読み替えられる
4. 1に戻る（繰り返し）→ サーバーが諦めて500

確かめられたのは「次の決まりを足すと、500が404に変わった」ことです。原因の説明は、あくまで私の推測です。

```
RewriteCond %{HTTP_HOST} ^(www\.)?suisuinavi\.sakura\.ne\.jp$ [NC]
RewriteCond %{REQUEST_FILENAME} !-f
RewriteCond %{REQUEST_FILENAME} !-d
RewriteRule ^ - [R=404,L]
```

- `!-f`、`!-d`：「ファイルでもなく、フォルダーでもない」という条件
- `RewriteRule ^ - [R=404,L]`：その場合は、何も書き換えずに「404（見つからない）」を返して終わる

これを2つ目の決まりの直後に入れました。

![.htaccess に404の決まりを足した最終版](media:a2-08-htaccess-with-404-rule.jpg)

**反省：** 最初の確認で「ある」ページしか見ていませんでした。**「ない」ページの返事も確かめる**ことを、これからの確認に入れます。

**② ブラウザは古い301を覚えている**

「301（永続的な転送）」は、ブラウザが覚えておくことがあります。そのため、設定を直したあとも、ブラウザだけが古い転送のまま動くことがあります。確かめるときは、`curl` を使うか、アドレスの末尾に `?x=1` のような印を付けて開く（別のアドレスとして扱われるので、覚えている転送が使われない）か、シークレットウィンドウで開きます。今回は、`?live=1` を付けて開きました。

**③ 自動デプロイの送り先が、まだ古いまま**

GitHubのActionsは、`main` に変更を送ると、アプリを `~/www/`（公開フォルダーの直下）に自動で送る設定になっています。これを `~/www/suisuinavi/` に送るように直す準備はできました（別のブランチで、コミットまで）。ただし**まだGitHubには反映していません**。反映するまでは、次に `main` へ変更を送ると、アプリが古い場所（`~/www/` の直下）にも送られてしまいます。ブログもアプリも壊れない見込みですが、**試してはいません**。同じファイルが2か所に並ぶことにはなります。

## 結果と、まだできていないこと

`curl` で確かめた結果です。

| アドレス | 結果 | 意味 |
|---|---|---|
| `suisuinavi.sakura.ne.jp/` | 200 | スイスイナビが表示される |
| `suisuinavi.sakura.ne.jp/robots.txt` など、無いもの | 404 | 「見つからない」（直す前は500） |
| `suisuinavi.sakura.ne.jp/michibiki/` | 301 | ブログへ案内される |

![curl で確かめた結果。アプリ用のアドレスは200、無いものは404、古いブログのアドレスは301でブログへ案内される。ブログ側は変わらず200。控えのファイルは403](media:a2-11-curl-results.png)

**まだできていないこと**

- 自動デプロイの送り先の変更を、GitHubに反映する（つまずき③）。
- アプリはまだ、クラウドのAPIにつながっていません。設定ファイル `config/cloud-config.js` の接続先は、空のままです。つなぐには、APIにドメインとHTTPSが必要です。
- どうしてアプリのファイルがなくなったのかは、分からないままです。

## 学んだこと

- **ドメインが2つあっても、公開フォルダーが同じなら、同じファイルを見ている。** 「別のサイト」と思い込まずに、まずコントロールパネルで、ドメインごとの公開フォルダーを確認する。
- **転送の決まりは、ほかのアドレスも巻き込む。** 「このアドレスだけ」のつもりでも、条件が広いと全部が転送される。
- **直す前に控えを取る。** `.htaccess` のように、ほかのサイトも支えているファイルは特に。
- **「ある」ページだけでなく、「ない」ページも確かめる。** 今回は、500で気づけた。
- **確認は、ブラウザだけに頼らない。** `curl` なら、ブラウザの覚えている転送に邪魔されない。
