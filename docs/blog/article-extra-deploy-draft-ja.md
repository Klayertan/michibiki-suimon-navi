## はじめに

**本記事は、さくらのクラウド検定 学生アンバサダーとして執筆しています。**

こんにちは。学生エンジニアです。

本編（#1 サーバー、#2 画面の公開、#3 データを受け取るAPI）とは別に、今回は**番外編**です。テーマは、**「スイスイナビの変更を、GitHubに送るだけで、さくらのレンタルサーバに自動で公開する」**仕組みです。

2本目では、スイスイナビの画面を、ファイルを手でアップロードして公開しました。ただ、手作業は、変えるたびに繰り返すことになります。そこで、**GitHub Actions** という仕組みで、これを自動にしました。

この記事のゴールは、次のとおりです。

> `main` というブランチに変更を送る → テストが通る → さくらのレンタルサーバのスイスイナビが、自動で新しくなる。ブログは、一切さわらない。

想定している読者は「GitHubは使っているけれど、自動で公開する仕組みは作ったことがない人」です。専門用語は、その都度、短く説明します。**うまくいかなかったことも書きます。** 実は今回、**実行する前に、公開先のフォルダーが間違っていることに気づきました**。その話が、この記事のいちばんの教訓です。

## 先に用語を整理

| 言葉 | ひとことで |
|---|---|
| GitHub Actions | GitHubが、変更があったときに、決めておいた作業を自動で実行してくれる仕組み |
| ワークフロー | 自動で行う作業の手順書。`.github/workflows/` の中のファイルに書く |
| デプロイ | 作ったものを、利用者が使える場所（サーバー）に置くこと。この記事では「公開」と同じ意味 |
| rsync | 2つの場所のファイルを、**違いのあるところだけ**そろえてくれるコマンド |
| SSH鍵 | パスワードの代わりに、「この鍵を持っている人だけ入れる」ようにする仕組み。公開鍵（サーバー側に置く）と秘密鍵（自分だけが持つ）の2つで1組 |
| Secrets | GitHubが預かってくれる、秘密の値の置き場。ワークフローからだけ使え、画面では読めない |
| ドキュメントルート | ドメインにアクセスしたとき、サーバーのどのフォルダーの中身を見せるか、という「入口のフォルダー」 |

## 全体の流れ

```
手元でコードを直す
   ↓  git push（main へ）
GitHub Actions が動く
   ① テスト（失敗したら、ここで止まる。何も公開されない）
   ② 公開（SSHで入って、ファイルを rsync で送る）
   ③ 確認（ブログのフォルダーが無事か、もう一度見る）
   ↓
https://suisuinavi.sakura.ne.jp/ が新しくなる
```

スイスイナビの画面は、**ビルド（変換）が要らない**作りです。`index.html`、`css/`、`js/`、`config/`、`data/` を、そのまま置けば動きます。だから、仕組みは小さく済みました。

## ①テスト：通らなければ、公開しない

最初の仕事は、テストです。`npm test`（Node.js 標準のテスト機能で、`tests/unit/` の中のテストを動かす）が、**ひとつでも失敗すると、そこで止まり、サーバーには何も送りません**。

```
  deploy:
    needs: test        ← テストが成功したときだけ動く
    if: github.ref == 'refs/heads/main'
```

ここで正直に書いておくと、**公開の条件になっているのは、この「ユニットテスト」だけ**です。ブラウザを動かすテスト（Playwright）は、時間がかかるため、公開の条件には入っていません。手元で動かすと、公開前から失敗しているテストがいくつかあります（水位の表示まわりなど）。公開の条件にするのは、それを直してからにする予定です。

## ②公開：順番と、安全装置

### 送る順番

送るのは、`data/` → `config/` → `css/` → `js/` の順で、**`index.html` を最後**にします。

```
rsync -avz --delete  js/  サーバーのjs/
```

`index.html` は、CSSやJSを読み込む入口です。入口を最後に置けば、**新しいページが、まだ届いていない部品を探しに行く、という瞬間が生まれません**。途中で通信が切れたら、そこで止まり、`index.html` は古いまま。古いページと、古い部品の組み合わせが残るだけです。

### `--delete` は、フォルダーを1つずつ

`--delete` は「送り先にだけあるファイルを消す」という指定です。便利な反面、**送り先を間違えると、関係ないファイルまで消えます**。そこで、`www/` 全体には使わず、`js/` のように**フォルダーを1つずつ指定**しています。`index.html` には `--delete` を付けていません。

### 3つの安全装置

1. **ホスト鍵の確認**：サーバーが「本物か」を、あらかじめ預けた情報（`SAKURA_KNOWN_HOSTS`）と照らします。空のままなら、公開しません。
2. **公開前の確認（ガード）**：送り先のフォルダーが無い、またはブログのフォルダー（`michibiki/`）が見つからないときは、「接続先を間違えている」とみなして止まります。
3. **公開後の確認**：終わったあとで、もう一度、ブログのフォルダーが残っているかを見ます。

パスワードは使いません。**このワークフロー専用のSSH鍵**を作り、秘密鍵はGitHubのSecretsに預けました。登録している名前は、次の4つです（ポートが22以外のときだけ、5つ目を足します）。

| 名前 | 中身 |
|---|---|
| `SAKURA_HOST` | 接続先のホスト名 |
| `SAKURA_USER` | ユーザー名 |
| `SAKURA_SSH_PRIVATE_KEY` | 専用の秘密鍵（パスフレーズなし。Actionsは入力を求められないため） |
| `SAKURA_KNOWN_HOSTS` | サーバーの正しい署名（`ssh-keyscan` で取得） |
| `SAKURA_PORT`（任意） | 22以外のポート |

【要追記】ここに、鍵を作ってSecretsに登録したときの経験（どこで迷ったか、など）を書いてください。値は書かないでください。

## 落とし穴：公開先のフォルダーが、間違っていた

2本目で書いたとおり、さくらのレンタルサーバでは、ブログ用のドメインと、スイスイナビ用のドメインが、**同じ公開フォルダー `~/www/` を指しています**。そこで、スイスイナビは `~/www/suisuinavi/` という専用のフォルダーに置き、`.htaccess` で「このドメインなら、あのフォルダーを見せる」と振り分けました。

ところが、自動公開のワークフローは、**今回の作業の前まで、`~/www/` の直下に送る**設定のままでした。

```
REMOTE_BASE: /home/suisuinavi/www          ← 古い設定（共有フォルダーの直下）
```

もし、このまま動かしていたら、**ブログの `index.php` のすぐ隣に、スイスイナビの `index.html` が置かれます**。ブログのトップページがどう見えるかは、サーバーの設定しだいで、私は確かめていません。確かめる前に、動かさないことにしました。

気づけたのは、ワークフローを有効にする前に、2本目の記録（開発メモ）と、ワークフローの送り先を、**見比べた**からです。直し方は、小さなものでした。

```
SITE_ROOT:   /home/suisuinavi/www              ← ブログも入っている共有フォルダー（確認用）
REMOTE_BASE: /home/suisuinavi/www/suisuinavi   ← 送り先はここだけ
```

あわせて、ガードも直しました。「送り先のフォルダーが、すでにある」ことを確かめ（**無ければ作らずに止まる**）、「ブログのフォルダーが、`SITE_ROOT` にある」ことも確かめます。

> 教訓：自動化は、**手作業で決めた「置き場所のルール」を、そのまま写さない**と、手作業よりも速く、間違った場所に届けます。自動にする前に、手作業の記録を読み返しました。

## 実際にやってみた（2026年10月12日）

### 有効にする

このワークフローは、GitHubの画面で**「手動で無効」**になっていました。それまでに10回動き、最後に動いたのは9月の初めでした。そのあとは止まっていました。【要追記】止めていた理由をご存じならここに。

「Enable workflow」を押して、有効にしました。**有効にしただけでは、公開されません。** 次に `main` へ変更が送られたときから、動くようになります。

### `main` に送る

直した版を `main` に送りました。すると、2つの作業が動きました。

| 作業 | 結果 |
|---|---|
| Deploy to Sakura（今回の本題） | 成功 |
| pages build and deployment（GitHub Pages。副系の公開） | 成功 |

Deploy to Sakura の中身を、1つずつ見ると、**全部で次のステップがすべて成功**していました。

| ステップ | 結果 |
|---|---|
| ユニットテスト（`npm test`） | 成功 |
| 公開用のSSH鍵を読み込む | 成功 |
| ホスト鍵（known_hosts）の設定 | 成功 |
| 送り先のガード | 成功 |
| `data/` `config/` `css/` `js/` を送る | 成功（4ステップ） |
| `index.html` を送る | 成功 |
| ブログのフォルダーが無事か確認 | 成功 |

### 公開された結果を、自分の目で確かめる

「成功」と出ても、**本当に公開されたかは、サーバーに聞いて確かめます**。`curl` で、アドレスにアクセスしました。

```
curl -s -o /dev/null -w "%{http_code}\n" https://suisuinavi.sakura.ne.jp/js/gnss/gnss-quality.js
```

- `-s`：余計な表示を出さない
- `-o /dev/null`：本文は捨てる
- `-w "%{http_code}\n"`：返事の番号（HTTPステータス）だけを表示する

| 確かめたこと | 公開前 | 公開後 |
|---|---|---|
| スイスイナビのトップ | 200 | 200（新しい機能のボタンが、ページの中に入っていた） |
| 今回増えた部品（JS・CSS、4つ） | （公開前は確かめていません） | すべて 200 |
| ブログのトップ（`sakurakai.sakuraweb.com`） | 200、55,249バイト | 200、**55,249バイト（同じ）** |

ブログのトップの大きさが、公開の前後で**1バイトも変わらなかった**ので、ブログは、さわられていないと言えます。

なお、`https://suisuinavi.sakura.ne.jp/michibiki/` は、公開の前も後も `404`（ブログ側のページ）でした。これは今回の変更とは関係なく、もともとそうなっています。

## うまくいかなかったこと・まだ残っていること

- **修正の置き場所**：2本目の作業で作ったはずの「送り先を直す変更」は、手元のパソコンの中だけにあり、GitHubに送られていませんでした。今回は、それを作り直して送りました。**「手元にだけある変更」は、無いのと同じ**です。
- **ブラウザテストは、公開の条件ではない**：上に書いたとおりです。
- **完全な切り替えではない**：入れ替えの途中で止まった場合は、`index.html` が古いまま残るだけです（上で説明した順番のおかげ）。ただ、新旧を一瞬で入れ替える「ブルー・グリーン」方式ではありません。止まったときは、もう一度動かせば、そろいます。

## 元に戻すには

サーバーには、公開の履歴を持たせていません。**戻すのは、Gitの仕事**です。

1. 問題のある変更を、`git revert` で打ち消して、`main` に送る → もう一度、自動で公開される
2. `main` の履歴を変えたくないときは、GitHubの Actions 画面から、**Run workflow** で、手動で動かす
3. それでもだめなときは、手作業でSSH・SFTPから直せる（自動化は、手作業の道を塞がない）

ブログのフォルダー（`michibiki/`）は、どの方法でも触れません。

## まとめ

- `main` に送ると、**テスト → 公開 → ブログが無事か確認**までが、自動で進みます。
- 安全装置は3つ（ホスト鍵・公開前の確認・公開後の確認）。パスワードは使わず、**専用の鍵**を使います。
- いちばんの落とし穴は、**自動化の送り先が、手作業で決めた置き場所とずれていた**ことでした。動かす前に、記録と見比べて気づけました。
- 「成功」の表示だけで安心せず、`curl` で**公開されたものを、自分の目で確かめる**ところまでが、公開の作業です。
