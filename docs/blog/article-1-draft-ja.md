## はじめに

**本記事は、さくらのクラウド検定 学生アンバサダーとして執筆しています。**

こんにちは。学生エンジニアです。

今回は、私が作っている水田の水管理支援Webアプリ「スイスイナビ」を使って、**「自分のMacの中でしか動かないPythonを、24時間動くサーバーに載せる」**ところまでをやってみました。ゴールは次の一点です。

> インターネットから `GET /api/health` を呼ぶと、さくらのクラウド上のPythonが `{"status":"ok","service":"sui-sui-navi-api"}` と返す。

想定している読者は「Pythonは少し書けるけれど、サーバーを立てたことはない人」です。専門用語はその都度、短く説明します。

そして、**うまくいかなかったことも全部書きます。** 実際、今回は何度かつまずきました。

## スイスイナビとは

スイスイナビは、みちびき（QZSS）の測位で水田の形と面積を測り、イネの生育ステージに合わせた水管理を支援するWebアプリの試作です。公開サイトは、さくらのレンタルサーバ上の静的ファイル（HTML・JavaScript）として動いています。

つまりこれまでは、**ブラウザの中だけで完結するアプリ**でした。圃場のデータもスマホやPCの中に保存されます。

でも、次のようなことをしたくなると、ブラウザだけでは足りません。

- 同じ圃場データを、スマホとPCの両方で見たい（アカウントと同期）
- センサーやドローンが、夜中でも水位や位置を送ってくる
- 何週間分もの水位の変化を溜めてグラフにしたい

どれも「いつでも起きていて、データを受け取ってくれるプログラム」が必要です。それが**サーバー**です。

さらに先には、**水の状態・ドローンの位置や状態・カメラ映像をリアルタイムに見られる画面**も作りたいと考えています。ドローンを画面から操作する仕組みも、現場のコンピューターで動くプログラムとして試作しています。ただし、**いずれもまだ実際の飛行では検証できていません**（水の状態やカメラ映像の表示は未実装です）。なお、ドローンの操作は、安全のため、インターネット上のサーバーは経由せず、ドローンのそばの現場のコンピューターで行う設計にしています。こうした機能は、画面だけでは作れず、データを受け取り続けるサーバー側のプログラム（Python）が必要になります。

## 問題：Pythonは「自分のMacの中」にしかない

スイスイナビには、アカウントや圃場データを扱うPython製のAPI（FastAPI）を、すでに書いてありました。テストも通っています。ただし、動かしていたのは**自分のMacの中だけ**です。これには困った点が3つあります。

1. **Macを閉じると止まる。** 蓋を閉じてスリープすれば、APIも止まります。
2. **外から届かない。** 自宅のMacは、インターネット側から直接つなげる状態ではありません。IPアドレスも変わります。
3. **開発機と本番機が違う。** 私のMacのシステムのPythonは3.9.6ですが、このAPIが想定しているのは3.12です。「自分の機械で動く」は、そのまま「本番で動く」ではありません。

そこで、**24時間つけっぱなしのコンピューターを借りて、そこでPythonを動かす**ことにしました。

## 解決策：サーバーを借りる。なぜ「さくらのクラウド」？

ちなみに、スイスイナビを最初に公開したのは**GitHub（GitHub Pages）**でした。無料で公開できるからです。ただし、GitHub Pagesが配信できるのはHTMLやJavaScriptなどの**静的ファイルだけ**で、Pythonのようなプログラムを動かすことはできません。ブラウザの中で完結するアプリならこれで十分でしたが、サーバー側でPythonを動かしたいとなると、別の場所が必要になります。いまはさくらのレンタルサーバで公開しています。

借りる先として、まず考えたのは次の3つです。

| 候補 | 向き不向き |
|---|---|
| さくらのレンタルサーバ（すでに使っている） | 静的サイトには最適。ただ、共有環境で常駐するPython/Dockerを自由に動かすのは難しい、と理解している |
| さくらのVPS | 小さなLinuxサーバーを丸ごと借りられる。公式表記で2GBプランは月額1,738円 |
| さくらのクラウド | VPSと同じく自分でLinuxを管理するサーバー。時間課金で、作成画面で見積もりが出る |

正直に書くと、**値段だけならVPSの方が安い**です。今回は、サーバー・ディスク・ネットワーク・パケットフィルタを自分で組み立てながら学べる、さくらのクラウドを選びました。

作成画面で出た見積もり（1コア・2GBメモリ・SSD 20GB）は次のとおりでした。

- 1時間 16円
- 1日 最大159円
- **1か月 最大3,190円**

「使った時間だけ課金され、月の上限がある」点は、学生が試すにはありがたい仕組みです。ただし、**サーバーを止めて課金が止まるのは、サーバー本体（CPUとメモリ）の分だけ**です。ディスクは削除するまで課金が続きます。使い終わったら、サーバーとディスクを削除します（詳しくは最後に）。

なお、サーバーの大きさ（CPUとメモリ）は**あとから変えられます**。管理画面の「プラン変更」から行い、公式マニュアルによると、**サーバーを一度停止してから**操作します。裏では「新しいプランのサーバーを作る → 設定を引き継ぐ → 古いサーバーを消す」が自動で行われ、**サーバーのIDは新しくなります**。また、1時間や1日といった課金の単位の中で何度も変えると、料金が増えることがあるそうです。ただし、私はまだ実際には試していません。参照：[公式マニュアル「サーバのプラン変更」](https://manual.sakura.ad.jp/cloud/server/plan-update.html)

## 先に用語を整理

| 用語 | ひとことで |
|---|---|
| サーバー | 人が操作する画面がなく、他のコンピューターからの要求に答え続けるコンピューター |
| 仮想サーバー（VPS） | 1台の物理サーバーを仮想的に分けて、自分専用に使えるサーバー。さくらでは「さくらのVPS」と「さくらのクラウド」のどちらでも借りられる（今回は後者） |
| SSH | 離れたサーバーに、暗号化された安全な通信でログインして文字で操作する仕組み |
| 公開鍵・秘密鍵 | 鍵のペア。**公開鍵**はサーバーに置く「錠前」、**秘密鍵**は自分のMacだけに置く「鍵」。秘密鍵は絶対に他人に渡さない |
| パケットフィルタ | サーバーの手前で通信を通す／捨てるを決める「門番」。さくらのクラウドでは仮想マシンの外側で動く |
| Docker / Docker Compose | アプリを「部品ごとの箱（コンテナ）」で動かす仕組み。複数の箱をまとめて起動・再起動できる。なぜ使うのかは、手順6で説明します |
| リバースプロキシ（Caddy） | 外からの接続を最初に受けて、裏側のアプリに渡す受付係。のちにHTTPSの処理もここで行う |
| FastAPI / Uvicorn | FastAPIはPythonのWebAPIを書くための道具、UvicornはそのPythonプログラムを実際に動かして待ち受けるサーバーソフト |
| ヘルスチェック | 「生きてる？」と聞くだけのAPI。今回は `/api/health` |
| localhost と インターネット | `localhost` は「自分自身」。自分のMacの `localhost` に出したものは、他人からは見えない |

## 全体像

```
        自分のMac ──(SSH: 22番)──┐
                                 ▼
 ブラウザ/curl ──(HTTP: 80番)─▶ [パケットフィルタ: 22と80だけ通す]
                                 ▼
                     さくらのクラウド上のUbuntuサーバー
                        ┌────────────────────────────┐
                        │ Caddy  ──▶  API(FastAPI)    │
                        │   :80       :8000(外には非公開)│
                        │               │             │
                        │               ▼             │
                        │         PostgreSQL(非公開)   │
                        └────────────────────────────┘
```

外に出ているのは **22番（SSH）と80番（HTTP）だけ**です。APIの8000番とデータベースの5432番は、サーバーの内側（`127.0.0.1`）でしか待ち受けません。

## 作業の前に：中身は先にMacで試した

サーバーに載せる前に、**同じ構成をMacのDockerで動かして**テストしました。「動かない原因がサーバーなのかコードなのか」を切り分けるためです。

- テスト：SQLite相手で109件成功（1件はPostgreSQL専用のためスキップ）、本物のPostgreSQL相手で110件成功
- 本番モードで、Caddy・API・PostgreSQLをまとめて起動して動作確認

この事前確認のおかげで、後のサーバー側の作業が「サーバーそのものの問題」だけに絞れました。

## 手順

### 1. SSH鍵を作る（Mac）

```bash
ssh-keygen -t ed25519 -C "sakura-cloud" -f ~/.ssh/sakura_cloud_ed25519
```

- `-t ed25519` … 現在よく使われる、短くて安全な鍵の方式
- `-C` … 鍵に付けるメモ
- `-f` … 保存する場所

実行すると、秘密鍵（`sakura_cloud_ed25519`）と公開鍵（`.pub`）の2ファイルができます。私のMacには `~/.ssh` というフォルダ自体がなく、これが人生初の鍵でした。

> 作成時にパスフレーズを聞かれましたが、Enterを押して空のままにしました。パスフレーズは、鍵ファイルが盗まれたときの最後の防御です。本番では必ず付けるべきです。
> ※パスフレーズは、鍵ファイルにかける「合言葉」です。作成時に表示される「SHA256:…」は鍵の「指紋（ID）」で、合言葉とは別のものです。

![※説明用に作った使い捨ての鍵（/tmp/demo_key）の画面です。実際に使った鍵とは別物で、作成後に削除しました。](media:12-ssh-keygen-empty-passphrase-demo.png)

### 2. サーバーより先に、ファイアウォール（パケットフィルタ）を作る

さくらのクラウドの共有セグメントにつないだサーバーは、**作った瞬間からインターネットに直接さらされます。**だから、門番を先に用意します。

管理画面の「ネットワーク → パケットフィルタ」で、プリセット「不要ポートのフィルタ（Linux用）」から作り、次のルールにしました。

| # | プロトコル | 宛先ポート | 動作 | 意味 |
|---|---|---|---|---|
| 1 | tcp | 22 | 許可 | SSH |
| 2 | tcp | 80 | 許可 | HTTP（API） |
| 3 | udp | （送信元123） | 許可 | 時刻合わせ（NTP） |
| 4 | udp | 68 | 許可 | DHCP |
| 5 | icmp | – | 許可 | ping |
| 6〜7 | tcp / udp | 32768〜61000 | 許可 | サーバーが外へ出た通信の「返事」 |
| 8 | fragment | – | 許可 | 分割されたパケット |
| 9 | ip | – | **拒否** | **上のどれにも当てはまらない通信は全部捨てる** |

ポイントは2つです。

- **ステートレス（通信の往復を覚えない）**：このフィルタは、サーバーから出ていった通信への「返事」も別の通信として扱います。だから6〜7の「返事を通す」ルールがないと、`apt` や `docker pull` が失敗します。
- **「どれにも当てはまらない通信は許可」**がデフォルトです。だから最後に「全部拒否」を置く必要があります。

プリセットにあった25番（メール送信）と110番（メール受信）は、メールサーバーを動かさないので削除しました。

![パケットフィルタの最終ルール（9本）](media:03-packet-filter-rules-ssh-http.png)

### 4. ログインする前に、外から見えるか確認

まだログインせず、Macから様子を見ます。

```bash
ping -c 2 <サーバーのIP>                 # 返事が来るか（往復 約13ミリ秒）
nc -z -G 4 <サーバーのIP> 22             # 22番ポートが開いているか
nc <サーバーのIP> 22 </dev/null | head -1   # SSHが名乗るバナーを見る
```

![※IPアドレスは <サーバーのIP> に置き換えています（実際のコマンドの出力を、IPの部分だけ置き換えたものです）。](media:13-step4-ping-nc-ip-masked.png)

結果は、pingに返事あり、22番は開いていて、SSHが「SSH-2.0-OpenSSH_9.6p1 Ubuntu…」と名乗りました（細かい版番号は、あとのパッケージ更新で変わることがあります）。サーバーが起きていて、門番が22番を通している証拠です。

### 5. ログインして、更新して、再起動する

```bash
ssh -i ~/.ssh/sakura_cloud_ed25519 ubuntu@<サーバーのIP>
```

![初回ログインの画面。指紋の確認に yes と答えると、プロンプトが出る（IPアドレスは伏せ、「初回」の確認は接続先の記録を空にして再現）](media:14-step5-first-login-ip-masked.png)

初回は「このサーバーの指紋を信用しますか？」と聞かれます。これは、なりすましを防ぐための確認です。今回は自分で作ったサーバーで、IPも管理画面から取ったものなので `yes` としました。

ログインしたら、まず**パッケージを最新にします。**

```bash
sudo apt-get update      # 「どんなソフトの新版があるか」の一覧を取得
sudo apt-get upgrade     # 一覧にもとづいて更新を実行
sudo reboot              # 更新を反映するため再起動
```

作ったばかりのサーバーなのに、**276個のパッケージ**が更新対象でした。「新品のサーバーは、もう古い」。最初の仕事は更新です。再起動後、約23秒でまたSSHがつながりました。

### 6. Dockerを入れる

**まず、なぜDockerなのか。**正直に書くと、Dockerを使うこと自体は、最初から決まっていました。スイスイナビのAPIには、`Dockerfile` と `docker-compose.yml`（箱の作り方と、複数の箱の起動のしかたを書いたファイル）が、すでに入っていたからです。そのうえで、今回の構成には次のような良い点があります。

- **3つの部品を、1つのコマンドで起動できる。**PostgreSQL（データベース）、API（FastAPI）、Caddy（入口）の3つを、`docker compose up` でまとめて立ち上げます。順番（データベースが正常になってからAPI、そのあとにCaddy）も守ってくれます。
- **Macで試したものを、そのままサーバーに持っていける。**Macのシステムのpythonは3.9.6で、APIが想定しているのは3.12です。箱の中に必要なPythonが入っているので、「自分の機械の都合」に左右されません。
- **サーバーのOSを汚さない。**PostgreSQLやPythonの部品を、OSに直接入れなくて済みます。やり直したくなったら、箱を消して作り直すだけです。
- **再起動しても、勝手に戻る。**`restart: unless-stopped` を付けておけば、サーバーを再起動したあとも、箱が自動で戻ります（手順9で確かめました）。

もちろん、良いことばかりではありません。Dockerという**もう一枚の層が増える**ので、仕組みを知らないと詰まります。たとえば、Dockerが公開したポートは、サーバーの中のファイアウォール（ufw）をすり抜けることがある、と公式の説明にあります。だから今回は、サーバーの外側のパケットフィルタを、最後の砦にしました。Pythonを直接入れて `systemd` で動かす方法もありますが、今回は試していません。

Dockerは、Ubuntu標準のリポジトリではなく、**Docker公式のリポジトリ**から入れました。

```bash
sudo apt-get install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
gpg --show-keys --with-fingerprint /etc/apt/keyrings/docker.asc   # ← 指紋の確認
```

最後の行が大事です。ダウンロードした「署名用の鍵」が本物かを、**Dockerが公式に公開している指紋と見比べます。**（今回は `9DC8 5822 9FC7 DD38 854A E2D8 8D81 803C 0EBF CD88` で一致しました。）一致を確かめてから、リポジトリを登録してインストールします。

```bash
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] \
  https://download.docker.com/linux/ubuntu noble stable" | sudo tee /etc/apt/sources.list.d/docker.list
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

入ったのは Docker 29.9.0 と Docker Compose v5.6.0 で、サーバーの起動時に自動で立ち上がる設定になっていました。

なお、`ubuntu` ユーザーを `docker` グループには**入れませんでした。**このグループに入ると実質的にroot（管理者）と同じ権限になるためで、`sudo docker ...` で使っています。

### 7. コードを置いて、起動する

まずMacからサーバーへコードを送ります。

```bash
rsync -az --exclude '.env' cloud_backend/ ubuntu@<サーバーのIP>:~/suisuinavi/cloud_backend/
```

`git clone` ではなく `rsync` にしたのは、新しいファイルを含むブランチがまだGitHubに上がっていないからです。（マージしたら `git pull` に切り替えます。）`--exclude '.env'` は、秘密情報の入るファイルを**送らない**ための指定です。

次に、**サーバーの上で**設定ファイル `.env` を作ります。パスワードなどの秘密は、**サーバー上で乱数から生成**し、Macにも画面にもGitHubにも出しません。

```bash
POSTGRES_PASSWORD=$(openssl rand -hex 24)              # データベースのパスワード（乱数）
SUISUI_CLOUD_SESSION_SECRET=$(openssl rand -hex 32)    # ログイン情報の秘密（乱数）
SUISUI_CLOUD_ENVIRONMENT=production                    # 本番モード
SUISUI_CLOUD_REGISTRATION_OPEN=false                   # 新規登録は今は閉じる
SUISUI_CLOUD_MAX_REGISTERED_USERS=10                   # 登録の上限
SUISUI_CLOUD_ALLOWED_ORIGINS=https://suisuinavi.sakura.ne.jp   # 呼び出しを許す画面の元
```

ファイルの権限は `600`（自分だけ読み書きできる）にしました。本番モードでは、`/docs`（自動生成のAPI説明ページ）を非公開にし、秘密が未設定なら**起動を拒否**する作りになっています。

そして起動です。

```bash
sudo docker compose -f docker-compose.yml -f docker-compose.vps.yml up -d --build
```

- `-f` を2つ … 基本の設定に、サーバー用の設定（Caddyの追加）を重ねる
- `up -d` … 裏で起動したままにする
- `--build` … 画像（イメージ）を作り直してから起動

これで、**PostgreSQL・API（FastAPI/Uvicorn）・Caddy**の3つのコンテナが立ち上がりました。データベースとAPIは「正常（healthy）」と表示されています。

APIの `/api/health` の中身は、たったこれだけのPythonです。

```python
class HealthResponse(BaseModel):
    status: str = "ok"
    service: str = "sui-sui-navi-api"

@app.get("/api/health", response_model=HealthResponse)
async def health() -> HealthResponse:
    return HealthResponse()
```

返すのは `status` と `service` だけ。本番か開発かといった内部の事情は、わざと返さないようにしています（攻撃者に手がかりを渡さないため）。

FastAPIは、書いたコードから**操作画面（Swagger UI）を自動で作ってくれます。**開発用にMacで動かしたものを開くと、こんな画面です。`/api/health` を開いて「Try it out → Execute」を押すと、実際にリクエストが飛び、返ってきたJSONがその場で見えます。

![Execute を押すと、実際のリクエスト（curl）と、返ってきた JSON・ヘッダーが見える](media:10-swagger-ui-health-response-dev.png)

ただし**本番のサーバーでは、この画面を閉じています。**`/docs` を開いても `404` です。公開された操作画面は、APIの地図を攻撃者にも渡してしまうからです。

### 8. インターネットから確認する

```bash
curl http://<サーバーのIP>/api/health
```

```json
{"status":"ok","service":"sui-sui-navi-api"}
```

**HTTP 200、0.15秒。** 自分のMacから、インターネットをはさんで、さくらのクラウド上のPythonが答えました。ブラウザでも同じ表示になります。

![ブラウザで /api/health を開くと、同じJSONが表示される](media:05-health-json-in-browser.png)

他の経路も確かめました。

| 確認 | 結果 | 意味 |
|---|---|---|
| `/docs` | 404 | 本番では説明ページを出さない |
| ログインなしで `/api/fields` | 401 | データはログインが必要 |
| 新規登録 | 403 | 今は登録を閉じている |
| 8000番・5432番に外から接続 | **5秒で応答なし（タイムアウト）** | 門番が捨てている |

最後の行が面白いところです。8000番と5432番は、そもそもサーバーの内側でしか待ち受けていません。もし門番がいなくても、外から来た接続は「拒否（すぐ失敗）」になります。**「応答なしで待たされる」のは、パケットが途中で捨てられた証拠**で、つまりパケットフィルタが効いています。

サーバーの内側からも確認しました（`ss -ltnp`）。外部に開いているのは22番（SSH）と80番（Caddy）だけでした。

メモリは、3つのコンテナ合計で約150MiB（Caddy 53・API 64・PostgreSQL 34）、システム全体で2GB中592MiBでした。**1GBのプランでも足りた可能性が高い**です（試してはいません）。

3つのコンテナには `restart: unless-stopped`（止められていない限り再起動する）を付けてあり、Dockerも起動時に自動で立ち上がるので、サーバーが戻れば中のPythonも自分で戻ります。データベースの中身（マイグレーションの状態）も残っていました。

## つまずいたこと

うまくいった話だけでは参考にならないので、詰まった点を書きます。

**① Caddyの後ろだと、全員が「同じ人」に見えた**
Macでの予行演習のときに見つけました。Caddyを前に置くと、APIのログに出る接続元が、全部Caddyのコンテナのアドレスになっていました。このAPIはログイン試行の回数制限を「接続元のIPごと」に数えているので、このままだと**全員が同じ枠を共有し、1人の失敗が全員を巻き添えにします。**
原因は、UvicornがCaddyの付ける `X-Forwarded-For`（本当の接続元を書いたヘッダー）を、標準では `127.0.0.1` からのものしか信用しないことでした。環境変数 `FORWARDED_ALLOW_IPS` で、Caddy経由のものを信用する設定にして解決し、**本番でも実際の接続元がログに出る**ことを確かめました。（偽の `X-Forwarded-For` を送っても、Caddyが上書きするので信用されません。）

**② ファイアウォールの編集が、保存されていなかった**
パケットフィルタの不要ルールを削除して「適用」したつもりが、途中でログインの有効期限が切れていました。再ログインして開き直すと、**ルールは元の11本のまま**。ルールの本数を数え直して気づきました。やり直して、**保存したら画面を読み込み直して確かめる**ようにしました。

**③ チェックしたつもりのチェックボックスが外れていた**
「SSHのパスワードログインを禁止」が、クリックしたのに外れたままでした。作成ボタンを押す前に、画面を上から全部見直して気づきました。そして**作成後の結果（`DisablePWAuth: true`）で確認**しました。セキュリティ設定は、クリックした記憶ではなく、結果で確かめるべきです。

**④ 管理画面のダイアログに、管理者パスワードが出ていた**
サーバー作成の途中で出る結果ダイアログに、**入力したパスワードが平文で表示されて**いました。スクリーンショットを撮る人は要注意です（私も写り込んだ画像を消し、そのパスワードは後で変更しました）。ブログ用の画像を撮るときは、**必ずこのダイアログを避けて**ください。

**⑤ ターミナルのタブを取り違えた**
複数のタブが同じ見た目で並んでいて、**サーバーに打つはずのコマンドを、自分のMacで実行してしまいました。**`passwd`（パスワード変更）で、サーバーではなくMacのログインパスワードを変えてしまったのです。気づいて元に戻しました。プロンプトが `ubuntu@suisuinavi-api` なのか、自分のユーザー名なのかを**打つ前に必ず見る**。以降は、サーバー用のコマンドを専用のタブで実行するようにしました。

## 後片付けと、費用の話

作業のために一時的にゆるめた設定は、終わったら元に戻しました。

- 作業中だけ `ubuntu` ユーザーが**パスワードなしで `sudo`** を使えるようにし、終了後に削除した

**費用について。**公式マニュアルによると、サーバーの料金は起動している間だけかかり、停止すると止まります。一方、ディスクは**削除するまで**課金が続きます。グローバルIPやパケットフィルタなど、ほかの項目が停止中にどう扱われるかは、そのページには書かれておらず、私は確かめていません。確実に課金を止めたいときは、使い終わったら**サーバーとディスクを削除**します。参照：[公式マニュアル「サーバの課金」](https://manual.sakura.ad.jp/cloud/payment/server-charge.html)

**クーポンについて。**さくらのクラウドには、クーポンを登録すると、書かれた金額分を無料で使える仕組みがあります。クーポンは、月の途中であとから登録しても、**同じ月の利用分に使える**と聞いています。ただし、公式マニュアルの[「クーポンの利用」](https://manual.sakura.ad.jp/cloud/payment/coupon.html)には、この点の記載が見つからなかったので、私は確かめていません。同じページには、残高が0になると、登録したクレジットカードに課金が始まること、クーポンには期限があることが書かれています。

## 結果と、まだできていないこと

**できたこと**
- さくらのクラウド上のUbuntuで、Python（FastAPI）のAPIが動いている
- インターネットから `GET /api/health` に `{"status":"ok","service":"sui-sui-navi-api"}` が返る（HTTP 200）
- 外に開いているのは22番と80番だけ。パスワードでのSSHログインは禁止
- 再起動しても、27秒で自分で戻る

**まだできていないこと（正直に）**
- **HTTPSではない。**今はIPアドレスへの平文のHTTPです。証明書は「名前（ドメイン）」に対して発行されるため、IPアドレスだけでは取れません。だから、ログインやデータの送信は**まだこのサーバーでは行いません**（新規登録も閉じています）。
- **バックアップはまだ取っていない。**
- 水位や位置を受け取るAPIは、まだ「予約された入口」（未実装）のままです。

## 学んだこと

1. **さくらのクラウドは、サーバー・ディスク・ネットワーク・パケットフィルタが別々の部品。**作成画面でそれらを組み合わせる。ホスト名・公開鍵・「パスワードでのSSHログインを禁止」は、「ディスクの修正」の欄で設定する。
2. **パケットフィルタは、サーバーの外側で動く門番。**通信の「返事」を覚えない（ステートレス）ので、返事を通すルールが要る。外から確かめて、22番と80番だけが開き、8000番と5432番はタイムアウトになることを確認した。
3. **課金は「時間単位＋月の上限」。**止めるとサーバー本体の分は止まるが、ディスクは削除するまで課金が続く。
4. **画面の設定は、作成結果で確かめる。**チェックを入れたつもりが外れていたり、編集が保存されていなかったりした。読み込み直して、作成結果の値を見る。
5. **新品のサーバーは、もう古い。**最初に更新して、再起動する（今回は276個）。
6. **Dockerのおかげで、Macで試した構成をそのまま載せられた。**再起動しても、約27秒で自動で戻った。
